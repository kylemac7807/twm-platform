## Fixed during build and review

1. **Form values never reached the handler in the headless tests.** Streamlit delivers a form's widget values only when the submit button is clicked; the tests were re-running between fields, which discarded them. The tests now set the fields and submit in one step and assert no error after the submit, so a silent refusal cannot pass.
2. **Marking a decision applied left its siblings pending.** A group decided in one go produces one decision row per queue item (the G-Cloud titles have two rows each); the export deduplicated them but `mark_applied` marked one. It now marks every live decision that says the same thing for the same item and client.
3. **The fixture for the second ledger copy** wrote into a directory that did not exist; the fixture now creates it.

## Known limits, deliberately left

- **A location decision applies to the rows that raised the flag** (same document and title), not to every row in the client with the same place, because the ledger does not store the place token (`attr_location_raw` is in the resolution result but not in the `observations` table). The rule reaches the other rows once it is codified and the set re-run. A one-column addition to the ledger would close this; left for the contract-terms merge so both streams' additions to `ledger.py` land together.
- **Web-page rows carry no position** in the ledger (the reader stores zeros; the table row and column are in the extraction's source_ref but not written to the observation). Inspect shows the quoted cells instead, honestly labelled. Same remedy as above.
- **Intake link decisions are recorded, not applied.** Confirming a suggested contract-set link writes the decision; the link itself is re-made on the next run. Correcting a classification does update the document record.
- **Extraction and reading queue items are read-only.** The action for those is a re-run, which is not yet started from the screen.
- **No login.** The analyst's name is typed once per session and recorded on every decision; identity comes with Azure.
- **85 of 87 promises are the test's name turned into words.** Good enough to read ("Title decision resolves every row for that client and recomputes counted"); a one-line docstring on each existing test would read better and is incremental work, not a blocker. Every new test gets one.
- **The `workbench` worktree and branch are unused** because Kyle chose to build here. Remove them when Kyle confirms, so the plan document and the folder agree.
- **Streamlit re-runs the whole script on every click**, so large ledgers will feel slower on the Inspect table; the volume run will say whether paging is needed.

## Rule compliance checked

- **Honest screens:** every abstention is shown in the system's own words (`detail` verbatim); no field is prefilled; the band default is unbanded; the close-up and page image come from the stored coordinates, not from text search.
- **Precision first:** reason required, name required, explicit count-bearing confirmation for bulk apply; a "leave flagged" decision is recorded and changes no row.
- **Flag then codify:** the workbench never writes to `taxonomy/` (tested by hashing the CSVs); decisions reach the taxonomy only through the export and the main session.
- **Append, never overwrite:** decisions supersede and remain; observations change only in their resolution columns; extraction columns are untouched.
- **Rates and money:** shown as stated with currency and unit; the derived reporting value appears only when the ledger holds a conversion, with its rate, date and source.
- **Data boundary:** one local SQLite file, no network, no model calls; the only exports are the codification CSVs and the page images rendered on the machine.
- **Guardrails:** the hook regenerated `PROMISES.md` on the step-7 commit and ran the suite; the regression checks cannot spend.

# Review addendum: v2, the designed web application (October 13, 2026)

**What changed.** Kyle rejected the Streamlit screens (ugly, not intuitive). The screens were rebuilt the same day as one page in plain HTML, CSS and JavaScript over a small FastAPI service (`work/workbench/plan-v2.md`), in the "Ledger" colour system he chose (deep teal-green accent, cool grey canvas, IBM Plex Sans, Plex Mono for anything quoted from a page), with none of the Vedra prototype's colours, words or logo. Streamlit is retired: `app.py`, `screens.py`, their eight tests and the dependency are gone; the ledger methods, the renderer, the promises list and the regression replays are unchanged.

**Proven by.** Five service tests (`tests/test_workbench_api.py`): a title decision through the API leaves the ledger exactly as the direct call does; bulk writes one decision row per queue item; a missing name, a blank reason or an unknown role is refused with nothing written; the page-image endpoint returns the boxed page 8 for the Texas row; the rules CSV matches the taxonomy headers and mark-applied clears the siblings. On the real ledger in the browser: Overview (483 rows, 458 counted, 21 waiting, 2 contract sets), Queue grouping the 19 items into 12 decisions with the evidence and the decision form beside the list, Documents opening the Texas set to its 7 documents and 53 rows and tracing row 1 to page 8 with the box and close-up, Rules empty as expected. 134 tests.

**Fixed during the build.** The list showed the model's whole abstention note (now shortened in lists, whole in the panel); the rate line doubled the currency for G-Cloud rows and showed an empty unit; wide tables now scroll inside their card so narrow panes do not scroll the page.

**Known limits, left.** The web page loads IBM Plex from Google Fonts and falls back to the system sans offline. Keyboard: arrows move the selection and Enter jumps to the reason; there is no shortcut to record. The Queue panel shows one close-up for a title group even when the group spans two rows (UK and offshore). Intake link confirmations are recorded, not applied (as before). No screen test drives the JavaScript itself; the service tests cover every write path and the browser check was by hand, with Kyle's step 6 still to come.

**For Kyle.** Step 6 as before: name in the top bar, Queue, work the 12 titles. Say what feels wrong in the first minute; that is the most useful feedback now.

# Review addendum: v3, after Kyle's feedback (October 13, 2026)

**What changed** (`plan-v3.md`, all six steps). Everything now starts from choosing a contract set: a landing list with a proposed, readable name (confirm or edit; file name beneath), a status (ready for review with its question count, in review as "n of m answered", complete), and per-set numbers once a set is open. Every answer carries a scope: this client (default), this contract set only, or everyone; the engine now consults saved answers before asking the model or a person on a re-run (`resolve_title` in `run.py`), which closes the gap where an answered title would have been asked again. Park, with a note and a Parked tab, replaces "can't decide yet" and "skip". The task card opens with a suggested role pre-selected and labelled (similarity to known titles and role names, both halves of a dual title; never the model), with alternatives beside it; technology tags found in the title are pre-ticked, several are allowed, common ones in the set come first, any other can be searched. "Why you are being asked" leads with one plain sentence; the system's own words are folded beneath. "Apply decisions" became **Global Framework Updates**, listing only "everyone" nominations, with place names explained as the client's rulebook. "Hello" is gone.

**Proven by.** Ledger tests: scope decides which rows an answer reaches and set/client answers are never exported; saved answers are found set-first then client, and re-answering supersedes; park and unpark; contract sets get a proposed name and a status that moves ready → in review → complete, and a confirmed name sticks. `tests/test_run.py`: a saved answer is used on a re-run with the model never asked, provenance in the row's notes, another client untouched, rules still first. Service tests: names, overview, suggestions (rules, halves, similarity), park and unpark through the API, scope validation. 141 tests. On the real ledger in the browser: both sets listed with sensible names ("Texas DIR – Accenture LLP · master agreement and exhibits · 2026"), the Texas workspace with 53 / 48 / 5 / 6, and the Operations card suggesting IT Operations Manager with IT Operations Analyst as the alternative.

**Judgement calls to flag.** (1) Re-answering an item with a narrower scope supersedes the earlier wider answer for that item; that is the designed "latest answer wins" behaviour, but it means narrowing withdraws the client-wide rule. (2) The year in a proposed name comes from the library manifest's vintage, so the Texas set says 2026 (the manifest's vintage for the 2026–2030 contract); analysts can edit. (3) Place-name answers still reach the engine only through the location rulebook file, so they stay on the Global Framework Updates screen under their own heading; a ledger lookup for places, like the one for titles, is a small follow-up. (4) Suggestions are token similarity; "Operations" → IT Operations Manager is plausible but not certain, and the card says so.

**Known limits, left.** No login (LATER 13); no registering of new contract sets from the screen (LATER); the Notes tab is read-only; page images for web rows do not exist by design. No automated test drives the JavaScript; the service tests cover every write path and the browser check was by hand.

**For Kyle.** Work the Texas set first: confirm or edit its name, then the five titles and the one document question. Watch for: whether the suggested role is right often enough to be worth pre-selecting; whether "this client" as the default feels right; whether Park is what you expected.
