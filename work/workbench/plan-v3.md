## Answers to the open questions

**A. What "Apply decisions" does, and why it is a separate step.** When you save an answer, every rate in this database that was waiting on it is updated at once and goes into the benchmarks. That part is immediate. But the role framework itself, the dictionary of roles and the table that says which vendor titles map to which role, is a set of versioned files kept outside this database, under version control, with an acceptance report that is regenerated every time they change. The workbench never writes those files, on purpose: a rule added to the framework is permanent, applies to every future document, and for anything that leaves a client's environment it must be checked by a person first. So "Apply decisions" is the hand-off list: the answers that have not yet been written into the framework. Today I append them with the taxonomy-change procedure and tick them off. With scope (B), only the answers you marked as applying beyond this contract set belong on that screen; an answer for one contract set is a rule for that set and lives here in the database. Proposed name: **Framework updates**, with the line "Answers you marked for this client or for everyone become rules in the role framework. This is the list waiting to be added."

**B. Two levels or three.** Three, because the system already has three places a rule can live: this contract set; this client's environment (in production, one TWM deployment is one client's Azure tenant, so "this client" means everything in that database); and the shared framework TWM keeps for everyone, which a rule reaches only through the promotion gate (seen at three or more clients, stripped of anything client-specific, reviewed by a person). Place names are already per client, and a vendor's job title usually means the same thing across one client's contracts, so the natural default for both is **this client**. "This contract set only" is the narrower choice for an odd title in one SOW; "everyone" is a nomination, not an instant change: it goes to the Framework updates screen. The trade-off is one more choice per answer; the mitigation is the default, so most answers need no choice at all. Kyle asked for local-by-default; I recommend "this client" as the default and "this contract set" as the deliberate narrower option. His call.

**C. The Technology field.** Yes, exactly as described. "Senior Java Developer" → role software developer, band senior, technology Java. The framework keeps technology out of role names (apart from the Packaged Applications family) so there are 129 roles rather than thousands, and the benchmark can still be cut by technology because it is recorded on each rate. Wording: **"Technology named in the title (optional)"**, with a one-line example underneath. The system already detects the tag when it can; after this change it is pre-filled.

**D. "Can't decide yet" versus "Skip" today.** "Can't decide yet" saves a decision row (your name, the time, your reason) with no role; the title leaves the To review list; its rates stay held back; the answer shows in the title's history; the title does not come back unless the document is run again. "Skip" saves nothing and moves to the next item; the title stays in the list. Recommendation: **merge them into Park**, with an optional note. Parking records who parked it, when and why, moves the title to a **Parked** tab you can return to, and keeps its rates held back. Arrow keys still move between items, so "Skip" needs no button.

**E. Home and Documents.** Yes, one place. The landing page is the list of contract sets with their status. Choosing one opens that set's workspace: its summary numbers, its name to confirm, and two tabs, **Review** (that set's questions, with the task card) and **Documents** (that set's files and rates, with the page trace). The top bar keeps a To review badge that counts the selected set's questions. A view across all sets can come later.

**F. "Hello".** Only on Home. It goes.
